## Implementation notes

The Cases group is the worked template; copy it for every later group.

- **Spec first.** Paths, verbs, parameter names and bodies come from `docs/openapi/thehive-docs.yaml`, not the plan. Grep for the path, then read the request/response schemas it references.
- **Models** go in `TheHive.Api/Data/{Group}/` (namespace `TheHive.Api.Data.{Group}`), one type per file: the output entity (e.g. `Case`), `{Entity}CreateRequest`, `{Entity}UpdateRequest`. Cover every property of the spec schema with `[JsonPropertyName("wireName")]` and XML docs. Required output strings default to `string.Empty`, collections to `[]`; optional values are nullable. Request properties are nullable (nulls are omitted by `TheHiveJson.Options`) except the schema's required ones, which use `required`. C# `required` only applies when constructing an object. `TheHiveJson.Options` clears `IsRequired`, so a response that leaves out such a member still deserializes.
- **Naming:** `{Entity}CreateRequest` / `{Entity}UpdateRequest` are reserved for an endpoint's **top-level** request body. A schema nested inside a body is named for what it is, e.g. `ShareSettings` (the spec's `InputShare`, nested in `CaseCreateRequest.SharingParameters`), `CustomFieldInput`. Entity types that would clash with BCL names are prefixed, e.g. `CaseTaskCreateRequest` / `CaseTaskStatus`, not `Task*`.
- **Clearing a field: `Optional<T>`.** Every update model uses `Optional<T>` (in `Data/Common/`) for each field the spec says can be cleared by sending `null` ("Send `null` to unset/unassign/clear"). Use a nullable `T`, e.g. `Optional<string?>` or `Optional<DateTimeOffset?>`. If the property is left unset it is omitted (a `TheHiveJson` type-info modifier handles this for every `Optional<T>`, so no attribute is needed). Assigning `null` sends `"field":null`, and assigning a value sends the value through the normal converters. Other update fields stay plain nullable and are omitted when null.
- **Types:** epoch-millisecond integers become `DateTimeOffset`/`DateTimeOffset?`; durations in ms stay `long`; string enums become tolerant enums with `Unknown = 0` first (use `[JsonStringEnumMemberName("wire")]` when the wire name is not the C# name, e.g. `autoShare`); integer "enums" (severity, TLP, PAP) stay `int` with named constants in `Data/Common/Severity.cs`, `Tlp.cs`, `Pap.cs`. Configurable values (case status names) stay `string`.
- **Shared value types** live in `Data/Common/` (`Access`, `AccessKind`, `CustomFieldValue`, `CustomFieldInput`, `SharingRule`, `Optional<T>`, ...). Reuse them; do not duplicate.
- **Interface** in `TheHive.Api/Interfaces/I{Group}.cs`. Refit attribute paths are relative, with no leading slash (`[Get("api/v1/case/{idOrName}")]`), and parameter names match the spec's path names. Every method takes `CancellationToken cancellationToken = default`. The client uses Refit's `UrlResolutionMode.Rfc3986`, which is what lets relative paths append to a path-prefixed BaseUrl.
- **Path values are escaped as a single segment** (`Uri.EscapeDataString`). `my case` becomes `my%20case`, `a/b` becomes `a%2Fb`, `a#b` becomes `a%23b`, `a?b` becomes `a%3Fb`, and `~` is not escaped (pinned by `CasesTests.GetAsync_EscapesIdOrNameAsOneSegment`). So a name containing `/` stays one segment, provided the server or proxy does not decode `%2F`. The dot segments `.` and `..` are **not** guarded on the client; ids and names are validated by the server. A comma-separated list in one path parameter (merge `{ids}`) is sent as `%2C`.
- **Entity types used by several groups** live in the folder of the group that owns the entity, not in the group that first needs them: `Data/Attachments/Attachment` (`OutputAttachment`), `AttachmentUploadResult` (`OutputAttachments`) and `AttachmentUpdateRequest` (`InputUpdateAttachment`); `Data/Observables/Observable` (`OutputObservable`); `Data/Procedures/Procedure` (`OutputProcedure`); `Data/Timeline/CaseTimeline` and `TimelineEvent`. Later groups (Alert, Task Log, Observable, Organization, TTP, Timeline) reuse them.
- **Bulk `...WithIds` bodies** that are the single-entity body plus `ids` derive from it and put `ids` first with `[JsonPropertyOrder(-1)]`, e.g. `CaseBulkUpdateRequest : CaseUpdateRequest` (so the single-entity request class is not sealed). Bulk bodies with their own fields are plain classes (`CaseBulkAccessRequest`, `CaseBulkApplyTemplateRequest`).
- **File uploads (multipart/form-data).** Mark the method `[Multipart]` and take each file as a Refit `MultipartItem` (callers pass `StreamPart`, `ByteArrayPart` or `FileInfoPart` with a file name and, ideally, a content type, and leave the part's own name unset). Name every part with `[AliasAs("wireName")]` matching the spec's form property. A spec array of files (`attachments: string[] binary`) is an `IEnumerable<MultipartItem>`; Refit sends one part per file, all with the same name, which is the OpenAPI multipart encoding for arrays. A JSON form field (such as `_json` in `POST /api/v1/case/import`) is the request model with `[AliasAs("_json")]`; Refit writes it with `TheHiveJson.Options` as an `application/json` part. A scalar form field (`canRename`) is a nullable parameter with a `null` default; Refit leaves out a `null` part. Template: `ICases.AddAttachmentsAsync`, `ICases.ImportAsync`. Uploads are never retried: `AuthRetryHandler` retries only replayable bodies (none, `StringContent`, `ByteArrayContent`, `FormUrlEncodedContent`, `ReadOnlyMemoryContent`, `JsonContent`, and the content Refit builds for `[Body]` objects, an internal push-stream type that re-serializes on each send and is identified by asking Refit's serializer), so stream and multipart bodies return their first response, which maps to `TheHiveApiException`. That avoids duplicate uploads and "stream already consumed" errors on non-seekable streams. (Retry policy in general: any verb on 429/503; other 5xx only for GET, HEAD, PUT, DELETE, OPTIONS, TRACE.) The per-attempt `Timeout` also covers sending the request body, so large uploads need a larger `Timeout`. Tests assert the request Content-Type `multipart/form-data` and each part's name, file name, content type and bytes, using `RecordedCall.ContentType` and `RecordedCall.Parts` from `StubHandler`. `StubHandler` reads each body once, and `Support/NonSeekableStream` exercises read-once uploads.
- **File downloads** return `Task<HttpContent>`: the caller reads the bytes or stream and the suggested name from `Headers.ContentDisposition.FileName`, and owns (disposes) the content. Error statuses still throw `TheHiveApiException` through the exception factory. Refit returns as soon as the headers arrive, so the per-attempt `Timeout` does not bound reading the body: document on each download method that callers should pass a `CancellationToken` to `ReadAs*Async`. Never log or echo query strings: they can carry secrets (export `password`), and `AuthRetryHandler` logs the path only. Template: `ICases.ExportAsync`. Tests queue the file with `StubHandler.EnqueueFile(bytes, contentType, fileName)` and assert the exact bytes, content type and file name, plus one failure status.
- **Optional bodies and JSON-or-multipart bodies.** Refit serializes a `null` `[Body]` as the JSON literal `null`, so an operation whose body is optional in the spec (`POST /alert/{alertId}/case`) takes a non-null request object whose properties are all optional; pass `new CaseFromAlertRequest()` (sent as `{}`). Where the spec accepts either JSON or multipart (`POST /alert`), only the JSON form is modelled; files are added with the attachments upload. Nested create types shared across groups (`ObservableInput`, `ProcedureInput`) live in the owning entity folder and always use the array form of spec fields that accept a string or an array.
- **Conditional downloads and 204 uploads.** A download with an optional header (`ITaskLogs.GetObservableAttachmentAsync`, `If-None-Match`) takes it as `[Header("If-None-Match")] string?`, omitted when null; a 304 is not a success status, so it throws `TheHiveApiException` with status `NotModified`. A multipart upload whose spec response is 204 (`ITaskLogs.AddAttachmentsAsync`) returns `Task`. Bool query parameters (`asZip`) are sent lowercase (`true`/`false`) by the client's URL parameter formatter (`TheHiveUrlParameterFormatter`, set on the RefitSettings); prefer `null` over `false` for `asZip`, since the spec allows an empty value and the server may treat presence as significant. Observable create endpoints that accept JSON or multipart (`IObservables.CreateInCaseAsync`, `CreateInAlertAsync`) model only the JSON form (`ObservableInput`, with an existing-attachment reference for files, which needs the attachment from the organization attachment upload `POST /api/v1/attachment` (`IOrganisations.UploadAttachmentsAsync`: pass the uploaded attachment's `Id` (`_id`, the `~…` value, matching the spec's InputAttachment example) as the reference `id`, with its `Name` and `ContentType`; (verify) not checked against a live server, and the hex storage id is what OutputAttachment calls `id`, so it is probably not the right value)); `dataType` is the optional query parameter the spec defines. Task log create likewise models only JSON (`TaskLogCreateRequest`).
- **`type` and `_type`.** When a schema has its own `type` property, `_type` maps to `EntityType` and `type` to `Type` (for example `Alert`); otherwise `_type` maps to `Type` (for example `Case`).
- **`customFields` object form.** The spec accepts `customFields` as an object (`{"name": value}`) or an array in several inputs (`oneOf`). No group models the object form; only the array form (`List<CustomFieldInput>`) is sent.
- **Top-level body reuse.** Where the spec uses a schema itself as an endpoint's top-level body (for example `POST /case/{caseId}/observable` and alert observables both use `InputCreateObservable`), reuse the one type (`ObservableInput`) instead of adding a duplicate `{Entity}CreateRequest`.
- **Opaque JSON and open value sets.** A schema the spec leaves undocumented stays raw JSON: `Dashboard.Definition` is a `JsonElement` (the spec types `definition` as an object, not a string; update uses `JsonElement?`). Permission names are plain strings in profiles and in `PermissionDescription.Name` (the spec enumerates them, but the list grows with releases, so a tolerant enum would lose new names). Custom field `options` are `List<JsonElement>` on output and `List<object>` on input (string, integer or float values). Organization create models only the JSON form (the multipart form adds an avatar file); set the avatar with update.
- **DELETE with a JSON body, text/plain results, 207 and secrets.** The unshare operations (`IShares.UnshareCaseAsync`, `UnshareTaskAsync`, `UnshareObservableAsync`, `DeleteManyAsync`) take a `[Body]` on `DELETE`, as the spec defines; Refit sends it as JSON. The API-key operations (`IUsers.GetApiKeyAsync`, `RenewApiKeyAsync`) return `Task<string>`, the raw `text/plain` body. A 207 is a success status, so `ITaxonomies.ImportZipAsync` returns it (as `TaxonomyImportResult`, with `Errors` filled) instead of throwing. Secrets (passwords in `UserCreateRequest`, `UserPasswordSetRequest`, `UserPasswordChangeRequest`; API keys) only ever travel in a request or response body, never a query string or path; the models are plain sealed classes with no `ToString`, so nothing prints them, and `User` never carries a secret (only `HasKey`, `HasPassword`, `HasMfa`).
- **Client property:** `public I{Group} {Group} { get; }` on `TheHiveClient`, assigned in the constructor with `RestService.For<I{Group}>(_httpClient, Settings);`.
- **Tests** in `TheHive.Api.Test/Groups/{Group}Tests.cs` using `StubHandler` and `TestClient.Create`: for each method assert verb, path and body, and map a full JSON sample (every property). Pass `TestContext.Current.CancellationToken`. Keep 100% line and branch coverage.
- **This table:** for each implemented row, fill in the Client method column as `` `I{Group}.{Method}` `` and the Test column as `` `{Class}.{TestMethod}` `` (several are allowed, comma-separated, each in backticks). Fill both or neither. `InventoryTests` resolves both by reflection, and checks that every method of every interface in `TheHive.Api.Interfaces` is listed, that no deprecated row is implemented, and that each Client method's Refit attribute has the row's verb and path (the path in backticks without its leading `/`, compared literally, so parameter names must match the spec). `docs/pending-tags.txt` lists the Group values whose rows may still be empty. **Remove the group's tag from that file when it lands**: the test then requires every non-deprecated row of the group to be filled, and a tag whose rows are all filled fails the test while it stays in the file. Labels such as `Case (+Timeline)` are separate tags. Notes on a row (such as `(verify)`) go in the Path column, after the path.

## Notes on mapping to the planned groups

Plan groups: Alerts, Cases, CaseTemplates, Tasks, TaskLogs, Observables, Comments, Attachments, CustomFields, Users, Organisations, Profiles, Procedures, Patterns, Timeline, Dashboards, Cortex, Query, Admin.

- **Attachments has no spec tag.** Attachment operations are scattered under other tags and are matched by path (`*/attachment*`): Alert (add/get/delete/download), Case (add/get/update/delete/download), Task Log (add/delete/get/download), Observable (get/download, tagged Task Log for get), Organization (`/api/v1/attachment` add/get/delete/download), User (`/user/current/attachments` temporary upload) and Case Report Template. The inventory keeps them under their spec tag; the implementer decides whether to expose them on `IAttachments` or on the parent interface.
- **Procedures = spec tag `TTP`; Patterns = spec tag `Att&ck`** (patterns, plus `/catalog` and `/pattern/import/attack`).
- **Singular tag to plural group:** Alert to Alerts, Case to Cases, Task to Tasks, Task Log to TaskLogs, Organization to Organisations (British spelling per plan), Dashboard to Dashboards, Query and Export to Query.
- **Multi-tag operations:** `Case | Timeline` (1, listed under Case) and `Share | Case` (5), `Share | Observable` (3), `Share | Task` (3) (listed under Share).
- **Spec tags outside the plan group list** (no planned interface): AlertStatus, CaseStatus, Alert Feeder, Email Intake, MISP, Function, Audit, Authentication, Branding, Case Report, Case Report Template, Config, Describe, License, Observable Type, Page, PageTemplate, Permission, Share, Status, Tag, Taxonomy, Views. Suggested folds are in the table above; confirm with the plan owner before implementing.
- **x-tagGroups tags with no operations in `paths`:** Features, GDPR, ThirdPartyProviders, Orchestrator, SlaRule, Authenticated and the Portal tags (Attachment/Case/Comment/Observable/User/Status (Portal)) are declared but have no operations in this spec version.
- Some spec tags are wrong on individual operations (e.g. `GET /api/v1/observable/{observableId}/attachment/{attachmentId}` and `GET /api/v1/log/{caseId}/attachment/{attachmentId}` are tagged Task Log). The inventory reproduces the spec as published.
